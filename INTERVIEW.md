# Interview questions: token-balance-script

## Q1. How do you represent token amounts in TypeScript, and what goes wrong with `number` or with ignoring decimals?

Answer: I keep amounts as `bigint` in raw units and only turn them into a decimal string when printing. On-chain, a token balance is an integer of up to 256 bits, while `number` is a 64-bit float that is only exact up to 2^53 - 1, about 9 × 10^15. With an 18-decimal token that limit is only about 0.009 tokens, and above it values silently round: `Number("9007199254740993")` gives `9007199254740992`, with no error. Decimals are a separate problem, because they're display metadata that the contract reports and the integer doesn't carry. USDC has 6 decimals, so a raw `2500000n` means 2.5 USDC, and my `formatAmount` test checks exactly that. The same raw value at 18 decimals is `0.0000000000025`, so assuming 18 for every token is wrong by a factor of 10^12. Another test formats `123456789012345678901234567890n` at 18 decimals and expects every digit back, which floats could not do.

## Q2. Walk me through what happens from `token-balance balance <token> <holder>` to the printed number, including every place it can fail.

Answer: `run()` first parses the arguments and validates both addresses, so wrong usage or a bad address exits with code 2 before any network call. It then calls `getTokenInfo`, which sends four `eth_call` requests for `name`, `symbol`, `decimals` and `totalSupply`, because the output needs the decimals and symbol, and then it reads the balance, so that's five calls in total. The `balanceOf` calldata is the 4-byte function selector, the first 4 bytes of the keccak256 hash of `balanceOf(address)`, which is `0x70a08231`, followed by the holder address ABI-encoded and left-padded to 32 bytes. viem sends that as `eth_call` with `{ to, data }` and the block tag `"latest"`, so the node executes it read-only against its newest block, with no transaction and no gas paid. The node returns a 32-byte `uint256`, viem decodes it to a `bigint`, and I print the raw value and then the formatted amount with the symbol. The network side can fail with an unreachable node or the 10-second timeout, and there are no retries, so that exits with code 1, as does a contract that reverts. An address with no contract is the subtle one: `eth_call` succeeds and returns `0x`, so a careless script could read that as a zero balance, but viem refuses to decode it and I print an error like `The contract function "name" returned no data ("0x")` and exit 1. A token whose `name()` returns `bytes32`, like MKR, also fails at decoding and exits 1, and a dishonest node could return a wrong number that I would not detect.

## Q3. How do ERC-20 Transfer events work at the log level, why can't one `eth_getLogs` filter express "from OR to", and how do you avoid counting a self-transfer twice?

Answer: A Transfer log has three topics plus a data field. Topic 0 is the keccak256 hash of `Transfer(address,address,uint256)`, which is `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef`, topic 1 is `from` and topic 2 is `to`, each padded to 32 bytes. `from` and `to` are in topics because they're declared `indexed`, which is what lets nodes filter on them, while `value` isn't indexed and sits ABI-encoded in `data`. `eth_getLogs` matches topics by position and combines different positions with AND. You can list alternatives within one position, but you can't say "topic 1 is me OR topic 2 is me". So I send two queries, one with `from = holder` and one with `to = holder`, and merge the results. A self-transfer matches both, so I merge into a `Map` keyed on `transactionHash:logIndex`, because the transaction hash alone would collapse separate transfers in one transaction. The merged list is sorted by block and log index, and the direction is labelled `in`, `out` or `self`.

## Q4. Could you rebuild every holder's balance by summing Transfer events instead of calling `balanceOf`? What breaks, and how would a production indexer handle it?

Answer: In principle yes for a well-behaved token, but in practice it isn't safe to assume. The first problem is data access, because you need logs from the contract's deployment onward and free nodes limit that: when I asked publicnode for 100000 blocks it replied `Invalid parameters were provided to the RPC method`, explaining that archive requests need a personal token. Other providers cap the block range or result size instead. The second is reorgs, because logs near the tip can be removed, so a running total that only ever adds can count transfers that no longer exist. The third is rebasing tokens like stETH, whose `balanceOf` changes without a Transfer event for each holder. The fourth is non-standard tokens: WETH9 emits `Deposit` and `Withdrawal` rather than Transfer when it wraps and unwraps, so summing Transfer alone gives wrong balances. A production indexer would fetch in chunks that shrink when the provider complains, use an archive-capable provider, and store its progress so it can resume. It would key rows on transaction hash and log index so reprocessing is safe, track block hashes to detect reorgs and roll back, treat only sufficiently confirmed or finalized blocks as settled, and reconcile against `balanceOf` regularly to catch tokens that don't follow the rules.

## Q5. How did you make Claude Code follow your formatting rules every time? Compare a CLAUDE.md instruction, a PostToolUse hook and a CI check.

Answer: I used all three, because each one covers a different gap. A `CLAUDE.md` instruction is only advice: Claude reads it and usually follows it, but nothing enforces it. A PostToolUse hook is a program Claude Code runs after every matching tool call, so my hook on `Edit|Write` is guaranteed to run, without Claude having to remember. It can't catch edits made outside those tools, like my hand edit in my editor or a file written through a shell command, and it can't format a file with a syntax error. Mine also only handles `.ts`, `.mts`, `.js`, `.mjs` and `.json`, so Markdown isn't covered. `format:check` in CI runs on every push and pull request and looks at the whole repo regardless of who made the change, so it's the backstop, but it only reports after the push and `.prettierignore` excludes `*.md` there too. The hook exits with code 2 on a syntax error because by then the edit has already happened, so it can't be blocked. Exit code 2 sends stderr back to Claude, so Claude sees the error and fixes it instead of carrying on with a broken file.
